# Review backlog (input to the sliced review pass)

Findings surfaced during integration that were worked around locally and must be verified/fixed at the source.

- [ ] **withdraw change-note `psi` fixture stale after domain rename.** The WASM workstream found that `withdraw`'s change-note `psi` fixture did not match the new `kakure.*` domain tags and computed it via `deriveCek`/`computePsi` in its own test instead. Verify every Noir/TS fixture literal that derives from `PSI_DOMAIN`/`ENC_DOMAIN` was regenerated (not just the ones the scrub's generator covered); add a parity test that recomputes each fixture from primitives.
- [ ] **`ComplianceKeyStale` removed from all paths** (workstream G): confirm the program still binds spends to the *current* compliance key via injection, and that key rotation mid-flight yields a clear client error (proof made under old key must fail as `InvalidProof`, documented).
- [ ] **`InvalidProof` mapping vs. verifier CPI error**: B and C reported contradictory behaviour; confirm with a litesvm test what error a client actually observes on a bad proof and align `decodePoolError` docs.
- [ ] **Hard-limits audit** for every instruction: serialized v0 message size (≤1232), CU (≤1.4M incl. real verifier ~600k), account sizes/rent; add asserts where missing (only `transfer_multisig`/`withdraw`/`deposit` are asserted in e2e today).
- [x] **Indexer event decoding under log truncation**: events use `sol_log_data`; confirm the worst-case tx (2 outputs) stays under the log budget and add a test. **Found and fixed** (workstream L, review slice 1, F-4): a real (non-mock) verifier CPI's own log volume was pushing a real deposit/spend tx's `NoteInserted`/`NullifierSpent` -- logged AFTER every CPI -- past Solana's per-transaction log budget, silently truncating them and making the indexer see zero notes even though the transaction succeeded (this is what broke the e2e scenario's step 4). Fixed by moving those emissions to BEFORE the verifier CPI in every proof-carrying handler (`programs/kakure_pool/src/processor.rs`) -- sound because a failing CPI reverts the whole transaction atomically, so a failed tx's log lines never land on chain regardless of where in the handler they were emitted (confirmed the indexer already skips `meta.err != null` transactions either way: `packages/indexer/src/ingest/ingest.test.ts`). Regression tests: `tests-litesvm/tests/pool_tests.rs`'s `deposit_note_inserted_log_lands_before_the_verifier_cpi` / `transfer_nullifier_spent_and_note_inserted_logs_land_before_the_verifier_cpi` assert the log order directly against a real litesvm-executed transaction's captured logs.
  - **Durable follow-up, not done here**: this fix reorders logging to reduce truncation risk, but does not eliminate it -- a sufficiently log-heavy verifier (or enough outputs) could still truncate an event that happens to be emitted early if something even earlier already ate the budget. The original I-4 design (a self-CPI instruction-data channel instead of `sol_log_data`) is immune to log-budget truncation entirely and should replace this ordering-based mitigation.
