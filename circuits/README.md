# circuits/

Kakure v1 Noir circuit workspace, vendored from an internal snapshot of the reference EVM
implementation (see `PROVENANCE.md`) and ported to Groth16 via [Sunspot](https://github.com/reilabs/sunspot).
Pin: `nargo 1.0.0-beta.22`.

## Layout

- `shared/` — the crypto/note/spend/FROST library used by every circuit; also the LeanIMT tree
  hash (`lean_imt_inclusion_proof`, Poseidon v1 — see below).
- `vendor/{ecdh,noir-edwards,poseidon}` — the three vendored money-path crypto libraries.
- `standard/{deposit,transfer,withdraw}`, `multisig/{transfer,split,join,withdraw}_multisig` —
  the 7 v1 circuits.
- `kat/lean_imt_poseidon_v1.json` — the depth-32 LeanIMT known-answer test, cross-checked between
  `shared/src/lib.nr` (Noir) and `scripts/gen_lean_imt_kat.mjs` (circomlibjs).
- `scripts/` — `gen_lean_imt_kat.mjs` (tree KAT), `gen_manifest.mjs` (`manifest.json`).
- `manifest.json` / `manifest.test.ts` — per-circuit `{circuit_id, public_input_count, vk_sha256}`
  drift test, AND (slice-2 F-1) the enforced guard that every committed `.vk`'s public inputs are
  actually bound by the proof — see "Every `pub` parameter must be constrained" below.
- `target/` — build output. `.json` (ACIR) and `.vk` are committed; `.ccs`/`.pk`/`.so`/`.gz`/
  `.proof`/`.pw` are gitignored (large or execution-specific).

## Every `pub` parameter must be constrained (slice-2 F-1)

A Noir `pub` parameter that is declared but never referenced by any constraint in the circuit
body compiles cleanly and looks completely normal in the ABI/witness — but under Groth16 it is
NOT bound by the proof. The verifying key's `K[i]` for that input is `Σ` (that wire's
coefficient, per constraint) `* [...]`; if the wire has zero occurrences in the R1CS, every term
in that sum is zero, so `K[i]` is the point at infinity and the verifier's `Σ pub_i·K[i]` term
ignores the input entirely — the proof verifies for **any** value of it. This bit `withdraw`:
`_recipient`/`_intent_hash` were declared `pub` and checked on-chain against the destination
account, but never referenced in the circuit body, so a relayer could swap both the proof's
`recipient` input and the destination account consistently and the pool's own check would never
notice. Noir's compiler does not warn about this (an unused `pub` parameter is exactly as valid
Noir as a used one), and gnark 0.14's own `CheckUnconstrainedWires` — which Sunspot's `compile`
relies on to catch exactly this — is presently a stub that always returns `nil` (a TODO upstream).

**Enforced gate**: `circuits/manifest.test.ts` parses every committed `circuits/target/<name>.vk`
(gnark's raw `WriteRawTo` wire format; see `circuits/scripts/vk.mjs`) and asserts that no
public-input `K[i]` is the point at infinity (an all-zero 64-byte G1 point). This runs in normal
CI/test flow (no Go toolchain needed) and is what actually blocks a regression from landing.

**Defence in depth, not enforced**: a local Sunspot branch,
`slice2-f1-public-input-binding-check` (in the `sunspot` checkout this repo's circuits are built
against, NOT vendored into this repo), adds a compile-time check in `ACIR.Compile()` that walks
the compiled R1CS and fails the build outright if any public input has zero occurrences in it —
catching the mistake before `sunspot setup`/`deploy` even run, for anyone building from that
branch. Kakure's own build does **not** depend on it (this repo's `justfile`/CI use stock
Sunspot); the manifest test above is the actual gate. Verified both ways against `withdraw`: the
pre-fix circuit (where `_recipient`/`_intent_hash` were unreferenced) fails that branch's
`sunspot compile` with "2 public input(s) ... have zero occurrences in the R1CS"; the fixed
circuit compiles clean.

When adding a new `pub` parameter to any circuit, give it a real constraint (an `assert` that
actually uses its value, not just a comparison the optimizer could theoretically eliminate) and
confirm `manifest.test.ts` still passes after rebuilding.

## Tree hash: Poseidon v1

Per the Kakure design spec §3.1, the LeanIMT node hash was switched from Poseidon2 (the reference
EVM implementation's choice) to Poseidon v1 (circom parameters), because Solana's `sol_poseidon` syscall is Poseidon v1, not
Poseidon2, and a hand-rolled Poseidon2 in SBF would blow the compute budget. Concretely,
`lean_imt_inclusion_proof` in `shared/src/lib.nr` calls
`poseidon::poseidon::bn254::hash_3([left, right, level])` (the vendored `poseidon` crate,
`src/poseidon/bn254.nr`) instead of `Poseidon2::hash([left, right, level], 3)`. Every other hash
in the system (note commitments, `psi`, nullifiers, owner hashes, the FROST challenge, DEM/KEM)
is unchanged Poseidon2.

`kat/lean_imt_poseidon_v1.json` gives the depth-32 root and each leaf's 32-entry sibling path for
a tree with leaves `1..8` inserted sequentially (plus a `genesis` empty-tree case), generated by
`circomlibjs`'s Poseidon and cross-checked byte-for-byte against a Noir replay
(`kat_lean_imt_poseidon_v1` in `shared/src/lib.nr`). This is the reference the program (B) and SDK
(C) LeanIMT implementations must match.

## Build pipeline

```
just build-circuits   # nargo compile -> sunspot compile -> sunspot setup (dev) -> sunspot deploy, all 7 circuits
just build-manifest   # regenerate circuits/manifest.json from the built .vk files
just verify-kat       # nargo execute (transfer_multisig KAT) -> sunspot prove -> sunspot verify
```

`GNARK_VERIFIER_BIN` must point at `sunspot`'s `gnark-solana/crates/verifier-bin` crate (set in
the root `justfile`). `sunspot setup` here is the **insecure dev** setup — no toxic-waste
mitigation — matching `manifest.json`'s `"setup": "INSECURE-DEV"` field; a release build must use
the `reilabs/trusted-setup` MPC script instead and update the manifest.

## End-to-end proof: `transfer_multisig`

`just verify-kat` runs the `kat_multisig_transfer_accepts` fixture from
`multisig/transfer_multisig/src/main.nr` (values copied into
`multisig/transfer_multisig/Prover.toml`) through the full pipeline:

```
nargo execute --package transfer_multisig   # -> target/transfer_multisig.gz (witness)
sunspot prove   transfer_multisig.json transfer_multisig.gz transfer_multisig.ccs transfer_multisig.pk
sunspot verify  transfer_multisig.vk transfer_multisig.proof transfer_multisig.pw
```

Measured on this build (dev setup, BN254, 70,396 constraints):

- **Proof**: 388 bytes.
- **Public witness (`.pw`)**: 780 bytes = 12-byte header + 24 × 32 bytes.
- **Sunspot setup**: ~4 minutes. **Prove**: ~3.5 minutes (constraint solve ~62s + Groth16 prove
  ~1100s of CPU across cores). **Verify**: ~3ms.

### `.pw` (public witness) byte layout

This is the format the prover (D) must produce and the pool program (B) must be able to
reconstruct/compare against, per I-1. Source: `GnarkWitness::from_bytes` /
`GnarkWitness::parse`, `gnark-solana/crates/verifier-lib/src/witness.rs`.

```
offset  size  field
0       4     nr_public_inputs   (u32, big-endian)  -- e.g. 24 for transfer_multisig
4       4     nr_private_inputs  (u32, big-endian)  -- always 0 in a public witness
8       4     entries_count      (u32, big-endian)  -- == nr_public_inputs
12      32*N  entries[0..N)      -- N = nr_public_inputs, each a 32-byte big-endian Field
                                     (canonical, < BN254 scalar field modulus), in the exact
                                     order the circuit's ABI declares its public inputs
                                     (first the `pub` fn parameters, in signature order, then
                                     the `pub` return tuple, flattened in order) -- this is
                                     I-1's flat Field[] layout.
```

For `transfer_multisig` (I-1 CircuitId 3, 24 public inputs): entry order is
`[compliance_pubkey_x, compliance_pubkey_y, nullifier, root, memo_leaf, memo_eph_x, memo_tag,
memo_cek_wrap, memo_ct0..6, change_leaf, change_eph_x, change_ct0..6]` — verified against the
program's declared public parameters (`compliance_pubkey_x`, `compliance_pubkey_y`) followed by
the return tuple in `main`'s declared order. Total file size = `12 + 24*32 = 780` bytes, matching
the measurement above exactly.

### `.proof` byte layout

Source: `GnarkProof::from_bytes`, `gnark-solana/crates/verifier-lib/src/proof.rs`.

```
offset  size  field
0       64    A   (G1 point, BN254)
64      128   B   (G2 point, BN254)
192     64    C   (G1 point, BN254)
256     4     commitment_count (u32, big-endian) -- 1 for every v1 circuit (each has exactly
                                                     one Pedersen commitment / no bit-decomposed
                                                     boolean commitments; see gnark's Groth16
                                                     "commitment" extension)
260     64*M  commitments[0..M) -- M = commitment_count, each 64 bytes (G1 point)
260+64M 64    commitment_pok    -- batched proof of knowledge of the commitments above (G1 point)
```

For `transfer_multisig`: `commitment_count = 1`, so total proof size =
`256 + 4 + 1*64 + 64 = 388` bytes, matching the measurement above.

### Solana verifier program instruction data

Per I-2 / `gnark-solana/crates/verifier-bin/src/lib.rs`, the verifier program's CPI instruction
data is simply `proof_bytes ‖ public_witness_bytes` concatenated — the program slices
`instruction_data[..instruction_data.len() - (12 + NR_INPUTS*32)]` as the proof and the remainder
as the public witness (`NR_INPUTS` is baked into the deployed program from its VK, so the split
point is fixed per-verifier, not self-describing). No accounts are read by the verifier program
itself; it is a pure `proof, public_inputs -> Ok/Err` check.

## Regenerated FROST fixture (`join_multisig`)

`join_multisig`'s `kat_multisig_join_accepts` test signs `msg_join(root_a, ...)`, and `root_a` is
computed via `lean_imt_inclusion_proof` over a non-trivial (non-zero-sibling) path — so switching
the tree hash invalidated the original vendored-snapshot FROST signature fixture. It was regenerated
with a throwaway single-signer (t=1) Schnorr witness: `z = (k + e*sk) mod SUBGROUP_ORDER`, computed
via a temporary Noir test (not committed) and confirmed against `verify_frost_spend` before being
baked into `kat_gpk()`/`kat_frost_r()`/`KAT_FROST_Z` in `multisig/join_multisig/src/main.nr`. See
`PROVENANCE.md` for the full note. No other circuit's KAT needed that regeneration: their
fixed-fixture Merkle paths all happen to use an all-zero sibling path (root == leaf), which is
hash-function independent. (Separately, workstream H's `kakure.*` domain-separator rename
regenerated every circuit's FROST/psi/leaf fixtures again -- see `circuits/scripts/gen_frost_kats.ts`
and `git log` for that pass; unrelated to the tree-hash switch documented above.)

## For workstream D (prover) and B (program)

- `.pw` and `.proof` byte layouts above are exactly what `sunspot prove` emits and
  `sunspot verify`/the verifier program consume; the prover should parse `.pw` into `Field[]` by
  simply reading the 24 (or however many, per `manifest.json`'s `public_input_count`) 32-byte
  big-endian chunks after the 12-byte header, in the order documented above.
- `manifest.json` gives, per circuit, the `circuit_id` (I-1), `public_input_count` (I-1), and
  `vk_sha256` (sha256 of the committed `.vk` file) — the pool program's verifier registry should
  be initialized with programs built from `.vk` files whose hash matches this manifest.
